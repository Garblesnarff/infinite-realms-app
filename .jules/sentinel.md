## 2026-06-18 - [IDOR and Existence Leakage in Condition Lifecycle Service]
**Vulnerability:** The `ConditionLifecycleService` methods (`applyCondition`, `removeCondition`, and `attemptSave`) were using a "check-then-act" pattern for authorization. While they performed pre-flight ownership checks, the actual database operations (`INSERT`, `UPDATE`, and `SELECT`) did not incorporate ownership filters, leaving the system vulnerable to race conditions and existence leakage.
**Learning:** Even with centralized authorization helpers, data-modifying and sensitive retrieval methods must implement defense-in-depth by ensuring every database operation is atomic and explicitly scoped to the authenticated user's permissions.
**Prevention:** Incorporate dual-ownership checks (`userId` AND `ownerId` for characters, campaign ownership for campaigns) directly into the `WHERE` clause of `UPDATE` and `SELECT` queries, and use `INSERT ... SELECT` patterns for `INSERT` operations. This ensures that the database itself gates the operation based on the user's identity in a single round-trip.

## 2026-02-15 - [WorkOS User ID UUID Validation Bypasses/Failures in Fog of War Router]
**Vulnerability:** The Fog of War router defined inputs using `z.string().uuid()` for `targetUserId` fields in endpoints like `reveal`, `revealBatch`, `conceal`, and `concealBatch`. Because the application uses WorkOS (not Supabase Auth) for identity management, user IDs are non-UUID strings (e.g., `user_01KAT...`). Strictly validating them as UUIDs in tRPC schemas resulted in valid target user IDs being rejected, causing authentication and state sharing failures between authorized session participants.
**Learning:** System user identifiers must always be validated based on the exact format of the backing authentication provider. Assuming all user IDs are UUIDs when transitioning/integrating third-party enterprise auth platforms like WorkOS can lead to severe operational issues.
**Prevention:** Always validate WorkOS-based user identifiers as `z.string()` (without `.uuid()`) in schemas and route input validations.

## 2026-03-20 - [Direct Supabase Campaigns Table Query on Frontend (RLS Bypass)]
**Vulnerability:** The world-builder generator services (`LocationGenerator`, `NPCGenerator`, `QuestGenerator`, and `WorldBuilderRepository`) were directly querying the `campaigns` table using `supabase.from('campaigns')` from frontend-side files. Since RLS is disabled on Supabase, these direct frontend queries bypassed Elysia server-routed access controls and would allow any client-side actor to query or guess campaign metadata.
**Learning:** Client-side files must never query Supabase tables directly using the anonymous client on secured tables, especially when RLS is disabled. All secure operations must go through server-routed APIs (like `userDataApi`) which securely authenticate requests using WorkOS JWTs on the backend.
**Prevention:** Migrate all direct Supabase frontend queries to server-routed REST/tRPC APIs, and enforce strict table-access checks via tests like `secured-table-access.test.ts`.

## 2026-07-25 - [Missing Module Import of verifyEncounterOwnership in Combat Status Routes]
**Vulnerability:** The combat status route file (`server-bun/src/routes/v1/combat/status.ts`) was using `verifyEncounterOwnership` to authenticate and authorize requests on multiple critical condition-related endpoints, but it was missing the import of this verification helper. This resulted in immediate runtime crashes (ReferenceError) when condition-management actions were invoked by players, leaving the condition lifecycle endpoint unstable.
**Learning:** Missing module imports for security and authorization functions can lead to complete denial of service or routing failures at runtime. Standard build/compilation toolchains that focus solely on frontend code paths can overlook backend runtime import bugs.
**Prevention:** Always include backend validation and integration smoke/boundary tests in CI pipelines, and ensure all route handlers have automated real-request tests covering authentication and authorization boundaries.

## 2026-07-26 - [IDOR in Session Message Retrieval and Creation]
**Vulnerability:** The session message REST endpoints (`/v1/sessions/:id/messages`) were lack-of-centralized-auth vulnerable, as they relied purely on inline database service-level checks inside the handlers. Without early route-level verification, this lacked a fail-secure architecture and could leak existence of resources or lead to authorization bypasses if a service method was updated without updating its ownership checks.
**Learning:** Centralized authorization (`onBeforeHandle` in Elysia) provides defense-in-depth and fail-secure guarantees at the route boundaries, preventing execution of complex business logic or service methods for unauthorized clients.
**Prevention:** Standardize all session-specific or character-specific REST sub-resources to utilize early, centralized `onBeforeHandle` hooks (such as `verifySessionOwnership` or `verifyCharacterOwnership`) to block requests before they are parsed or routed to services.

## 2026-07-27 - [IDOR and Resource Exposure in Game Session and Handout Routes]
**Vulnerability:** The core session REST endpoints (`/v1/sessions/:id/*`) and handout delivery REST endpoints (`/v1/sessions/:id/handout-actions` / `/v1/sessions/:id/journal`) relied purely on inline manual service-level or conditional authorization checks inside individual route handlers. This manual approach increased the surface area for IDOR vulnerabilities and potential existence leakage of session or campaign data.
**Learning:** Decoupling session loading and authorization boundaries from individual handler logic ensures that any request referencing a specific session ID must pass authentication and ownership gates at the Elysia route-level. This prevents leaking the existence of game assets and enforces uniform security posture.
**Prevention:** Implement centralized `.resolve()` and `.onBeforeHandle()` hooks in Elysia router definitions to authenticate, fetch, and verify dual-ownership of resources early, protecting all sub-resources and mutations uniformly before reaching any business logic.
